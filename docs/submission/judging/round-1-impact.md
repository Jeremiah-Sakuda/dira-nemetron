### 1. High — reconcile the judge materials with the actual v2 deployment

**Evidence:** [README](../../../README.md#try-it) says Google OAuth still needs configuration and its verification table says neither provider was exercised. [judge-checklist.md](../judge-checklist.md) likewise says actual provider changes need verification. The Calendar and Gmail evidence establish narrower, actual provider results: one Calendar source-change repair, and self-addressed Gmail draft creation/recovery from an operator-provisioned plan. Meanwhile [significant-update.md](../significant-update.md), rows 24–29, says Cloud Run was deleted, places the current stack on a Nebius VM/Serverless Jobs and presents Hermes chat and mirrored Skills as complete. [devpost.md](../devpost.md), line 43, also retains the retired Nebius CPU backend despite its later current-deployment paragraph correctly naming Cloud Run/Neon. The October 16 migration record and round context explicitly contradict those claims.

**Why it affects judging:** The substantial update is credible—accounts, authenticated approvals, private memory, model repair proposals and a full web workflow are more than a model swap. Inconsistent status makes a judge question which of those changes actually exist and which path produced the proof.

**Action:** Rewrite the significant-update explanation and all primary status summaries around the same dated deployment. Distinguish implemented features, actual provider checks, simulated public actions and separately measured sandbox checks. Link the frozen v1 baseline and a fixed v2 snapshot as well as the moving comparison.

**Acceptance:** README, Devpost draft, checklist and significant-update table agree on current hosting, Google verification scope and inactive Hermes mirror. No current claim says OpenShell surrounds Cloud Run, that Gmail inbox intake/sending was verified, or that Nebius VMs remain active. The significant-update text identifies both the inherited deterministic engine and the demonstrated new capabilities.

### 2. Present the student problem and its demonstrated resolution

**Audience:** a student coordinating coursework, recruiting and a team deliverable.

**Problem:** a changed exam date removes preparation time, breaks an interview buffer and conflicts with work another person depends on.

**Presentation:** follow source → interpreted change → affected commitments → approved repair → independently read-back result. Show restored study time, the delegated task and the interview request's explicit counterparty status. This sequence makes the problem, audience and solution concrete under the official Potential Impact criterion.

**Acceptance:** a judge can explain whose problem Dira addresses, why the commitments are connected, and how the demonstrated repair addresses the disruption. Keep the synthetic integration label alongside the demonstration.

### 3. High — put the useful Ultra contribution into the judge journey

**Evidence:** The [bounded repair corpus](../../evidence/2026-10-13-ultra-bounded-repair-eval.json) reports 7/7 resolved scenarios, 3/11 acceptable Ultra proposals and two Ultra winners. `overlap-flexible-block` is the specific model-expanded case highlighted by README and Devpost. The default `48-hour-shock` case selects a deterministic plan; the checklist asks judges to watch an Ultra proposal and a labeled adversarial rejection, without directing them to the case the enumerator cannot solve.

**Why it affects judging:** The non-obvious NVIDIA contribution is the model proposing a useful repair outside the four fixed shapes. A visible model call or rejection alone does not demonstrate that extra capability. “7/7 resolved” can also be mistaken for seven successful model plans if the denominator is separated from the explanation.

**Action:** Provide an accessible recorded or credential-free evidence view of the overlap case, with the enumerator result, structured Ultra intent, resolved provenance, gate verdict, selected plan and simulated read-back shown together. A live rerun is optional; any stored view must be unmistakably labeled. Give it an explicit step in the checklist and video.

**Acceptance:** Within one short judge step, the reviewer sees a measured case with no deterministic repair and a selected feasible Ultra repair. The same view shows 3/11 acceptable proposals and 2/7 selected repairs, identifies the synthetic integrations and date, and avoids implying those rates generalize.
